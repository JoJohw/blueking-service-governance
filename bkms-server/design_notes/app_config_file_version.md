# 应用配置文件版本管理设计

## 背景

当前 `app_config_files` 只保存配置文件当前状态，无法处理：

- 某个配置文件历史上改过什么
- 当前版本是从哪个版本演进而来
- 某次回滚到底回到了什么状态
- overlay 文件在当时依赖的是哪个 base 版本

为了支持版本列表、版本对比、回滚、历史删除和更清晰的审计，需要引入独立的版本链。

## 适用范围

版本管理作用于所有使用 `app_config_files` 的应用类型，包括 `trpc`、`taf`、`helm`。

版本记录关注的是 **BKMS 自身维护的状态变化**，而不是单纯复制外部系统的内容。

## 设计目标

- 主表表达当前生效状态
- 版本表表达完整历史链
- 当前版本也必须在版本表中能找到
- 历史版本不可变
- 回滚是一次新的状态变化，因此必须生成新版本
- 审计只做追踪，不作为恢复依据

## 核心模型

主表保留当前状态相关字段，例如：

- `currentVersion`
- `updater`
- `updatedAt`

版本表保留历史链相关字段，例如：

- `appConfigFileID`
- `version`
- `description`
- `operationType`
- `rollbackFromVersion`
- `baseVersion`

其中：

- `currentVersion` 表示主表当前正在生效的版本号
- `appConfigFileID + version` 唯一确定一个历史版本
- `baseVersion` 用于解释 overlay 文件在当时依赖的 base 内容语境

## 本地内容与 BSCP 内容

### local

`contentSourceType=local` 的文件由 BKMS 直接维护内容，状态变化属于版本管理范围。

### bscp

`contentSourceType=bscp` 的远端内容本体不由 BKMS 保存，因此版本管理的重点不是复制远端内容，而是记录 **BKMS 侧可观测、可回滚的状态变化**：

- `bscpConfig` 引用关系变化
- 本地 `overlayContent` 变化
- 文件名、base 引用等文件属性变化

换句话说，`bscp` 文件也应该有版本记录，但版本记录表达的是：

- 当时指向了哪个 `biz/service/config`
- 当时本地 overlay 是什么
- 当时文件级关系是什么

而不是把外部 BSCP 的完整内容拉回 BKMS 存一份历史副本。

## 回滚需要生成新版本

如果把当前状态直接改回旧版本，会有几个问题：

- 无法表达“这里发生过一次回滚”
- 当前状态变化没有独立历史节点
- 多次回滚后版本链会失去可解释性

更合理的链路是：

- `v1` create
- `v2` update
- `v3` update
- `v4` rollback from `v2`

这样“当前状态”和“历史来源”是同时清晰的：

- 当前生效的是 `v4`
- `v4` 的来源是 `v2`
- `v2` 本身仍保持不可变

## overlay 与 base

overlay 文件有两层语义：

1. **在线关系**
   `baseAppConfigFileID` 表示当前 overlay 正在依赖哪个 base 文件

2. **历史解释**
   `baseVersion` 表示某个历史版本生成时，它所处的 base 版本语境

这里不把在线引用改成某个 base 历史版本，原因是：

- 在线关系描述的是当前系统如何工作
- 历史解释描述的是当时那次变更在什么上下文下生成

两者不能混在一起。

## 删除历史版本

删除历史版本采用逻辑删除。

- 仍然保留审计和追踪信息
- 不破坏版本号链路
- 可以在列表层默认隐藏删除记录

当前版本默认不允许删除，因为它代表主表正在引用的生效状态。

## 一致性边界

当前阶段仍采用“版本表写入 + 主表更新”的分步方式，代码中保留事务改造入口。

- 版本链是主能力，后续可以通过事务或补偿进一步增强一致性
- 领域编排要尽量收敛到下层，避免在 handler 中重复拼接写入流程
